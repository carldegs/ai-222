Introduction

1. From written text to model input

Imagine we want a model to work well with scientific articles, everyday conversation, and several languages. Choosing a larger model does not settle which writing it learns from, how a rare word is split, or how a sentence becomes numbers. This lecture studies those choices. We will follow three ingredients: training data, the text examples; the tokenizer, which defines the text units; and the model, which processes their numerical representations.

Data

Examples the model learns from. Quantity matters, but source, quality, and representation matter too.

Tokenizer

A repeatable conversion between text and a sequence of discrete tokens or token IDs.

Model

A system that maps token context to useful representations or a probability distribution for a prediction.

Recap · Language modeling

The prediction objective we are building toward

Recall the central idea from the previous lecture: an autoregressive language model predicts a token from the earlier tokens. Multiplying these conditional probabilities gives the probability of a complete sequence. Slide 12 restates that objective:

P(x₁, …, xL) = P(x₁) P(x₂ | x₁) ··· P(xL | x₁, …, xL₋₁)
\[p(x_1,\ldots,x_L)=\prod_{t=1}^{L}p(x_t\mid x_1,\ldots,x_{t-1})\]

The equation tells us what the model predicts. This lecture asks what supplies those tokens, how they become numerical inputs, and which model arrangement processes them. Keep the distinction clear: tokenization defines the units; the language model learns probabilities over sequences of those units.

Before architecture

2. What text is the model learning from?

Let’s start where the slides start: the training text. A corpus is a collection of documents used as data. Web-scale sources such as Common Crawl provide huge amounts of varied writing, but size alone does not tell us whether that collection suits our goal. Slide 4 asks whose writing is represented. Web contributors are not a balanced sample of all people, languages, or topics, so a large corpus can still leave major gaps.

The next examples—WebText, C4, GPT-3’s data mixture, and The Pile—show different ways to assemble a corpus. Filtering removes text according to chosen criteria, while deduplication reduces repeated material. Both change what the model will see. In slide 7, C4 illustrates how a raw web crawl becomes a selected training collection. Use the questions below to read each dataset example.

Text becomes numbers

3. Tokenization defines the model’s reading units

We have selected the text. How does the model read it? Slide 18 introduces tokenization: splitting a string into units and mapping those units to integer IDs. In the simple word-level example, “the cat sat on the mat” becomes six tokens with IDs [0, 1, 2, 3, 0, 4]. Notice that “the” gets ID 0 both times. The ID identifies a vocabulary entry; its numerical size does not describe the word’s meaning.

Coverage

Can it handle the needed languages, symbols, numbers, code, and unseen words?

Efficiency

How many tokens does a typical input become? More tokens mean more sequence positions to process.

Reversibility

Can the original text be reconstructed, including spaces and punctuation? The lecture highlights this for SentencePiece.

Now look at slide 21. Choosing these units creates tradeoffs: we need to represent the text accurately without making ordinary inputs unnecessarily long. Real systems often use word pieces, characters, or bytes rather than whole words alone. A good tokenizer also needs consistency (the same text maps to the same IDs), sensible boundaries (punctuation, capitalization, and meaningful word pieces are handled predictably), and robustness (unusual Unicode, emoji, code, and noisy input still work). It should not make non-English writing disproportionately expensive in tokens. A tokenizer for code must preserve details such as indentation; one for medical text should avoid needlessly fragmenting frequent clinical terms. Tokenization must also be fast enough for large-scale training and use.

Why not simply split on spaces? Whitespace is not a universal word boundary: some languages do not separate every word with a space. This is why splitting only on spaces is a poor general solution. A small vocabulary makes many long sequences; an enormous vocabulary gives rare pieces little training data. Subword methods balance these pressures.

One word can occupy several positions. A common word may be one token, while an uncommon word may split into pieces. Token IDs are lookup labels, not numerical meanings: ID 8 is not twice as meaningful as ID 4.
How the units are learned

4. Build larger tokens from frequent pairs

How can we learn useful word pieces from the corpus? Slides 30 and 31 introduce Byte Pair Encoding (BPE). Start with small units, count adjacent pairs, merge a frequent pair into a new unit, and count again. Repeating this procedure builds a vocabulary of recurring pieces. The toy corpus is “the cat,” “the cap,” “the bat.” Because “the” occurs in each string, its letter pairs are good candidates for early merges. This shows how a learned vocabulary compresses frequent patterns into fewer positions. It does not mean the token “the” has been assigned a semantic meaning by the merge algorithm.

Another route: SentencePiece and the unigram model

Slide 34 introduces SentencePiece, a tokenizer framework that can use BPE or a different method called a unigram language model. Here, “unigram model” refers to probabilities over token pieces used for segmentation; it is not the next-token language model we will train afterward. Instead of growing a vocabulary by pair merges, the unigram approach begins with a generous set of candidate pieces. It assigns each piece a probability, considers ways to split the training text into those pieces, and repeatedly removes pieces whose removal harms the fit least. Single-character pieces remain as a fallback, so unfamiliar text can still be represented. The lecture calls the probability-estimation step expectation–maximization (EM): alternate between estimating useful segmentations and updating piece probabilities.

To see what those piece probabilities are for, consider ababc. It might be split as ab | ab | c or a | b | ab | c. A segmentation made of more probable pieces receives a higher score; the tokenizer selects a suitable segmentation using its learned probabilities. This is a different learning rule from BPE’s frequent-pair merging. SentencePiece also treats whitespace as part of the text it encodes, which helps it reconstruct the exact original string after decoding.

Why byte or character fallback matters: Unicode contains far more symbols than a practical learned vocabulary can dedicate whole tokens to. Breaking rare symbols into base characters or bytes keeps them representable, though often at a higher token cost.
Token-count comparison: If a sentence uses 9 tokens under one tokenizer and 4 under another, the reduction is (9 − 4) / 9 = 55.6%\((9-4)/9\approx55.6\%\) for that sentence. A different sentence may split differently.
IDs become features

5. Embeddings turn discrete tokens into vectors

We now have tokens and IDs, but an ID is only a label. Slide 47 shows the next step: an embedding table stores a learned vector for each vocabulary entry. An ID selects a row of that table. If we look up IDs [0, 1, 0], we retrieve the first vector, the second vector, and the first vector again. For a sequence of L\(L\) tokens with d\(d\) features per vector, stacking the rows gives an array of shape L × d\(L\times d\).

ID sequence: [0, 1, 0] Embedding lookup: [E₀, E₁, E₀] If E has |V| rows and d columns, output shape = 3 × d.
\[E\in\mathbb{R}^{|\mathcal V|\times d},\qquad [0,1,0]\mapsto[E_0,E_1,E_0]\in\mathbb{R}^{3\times d}\]

Keep the lookup step separate from what the model does afterward. The same ID starts with the same lookup vector. Slide 50 shows why the later contextual representation can be different: after the sequence model processes surrounding words, the vector for a position can depend on the sentence. Thus “bank” can represent a financial institution in one sentence and a riverbank in another.

Same lookup, different context

Choose the architecture by task

6. Encoder, decoder, or both?

Our sentence has reached the model as a sequence of vectors. Slide 46 now asks which model arrangement we use. The three families are encoder only, decoder only, and encoder–decoder. To distinguish them, ask what context each position can use and what output we want: a decision about supplied text, a continuation, or a separate generated sequence. Slides 51–53 give examples of these uses.

FamilyTypical access and outputGood example
Encoder only (BERT)Uses both sides of an available input for contextual understanding; commonly trained with masked-token objectives.Classify sentiment or compare two statements.
Decoder only (GPT)Uses earlier tokens when predicting the next token; naturally generates a continuation.Complete a prompt or write text.
Encoder–decoder (T5, BART)Encoder reads the input; decoder generates a new sequence while conditioned on it.Translate, summarize, or turn a table into text.

Let’s connect the table to how the models operate. An attention mask controls which positions may exchange information. An encoder token may use earlier and later input positions, so a masked-token task can ask it to infer a hidden word from both sides. A decoder token is blocked from future output positions; training asks it to assign high probability to the actual next token (maximum likelihood). At generation time it appends one predicted token, then repeats. In an encoder–decoder model, the encoder first represents the supplied input; the decoder reads that representation while generating the separate output from left to right.

Check your understanding

7. Can you explain the whole path?

Let’s check the whole path, rather than memorizing the names in isolation. Given a piece of text, explain where it came from, how it becomes tokens and IDs, what the embedding lookup returns, and how the chosen model uses the context. Try each question before opening the explanation.

Why might web-scale data still produce an uneven model?

The web is large but its contributors are not a balanced sample of all languages, populations, or topics. Filtering can improve quality while changing coverage. A model learns patterns in the resulting corpus, so collection and cleaning choices affect what it learns.

Explain tokenization and the role of token IDs.

Tokenization divides text into units such as words or subwords. A vocabulary maps each unit to an integer ID so the model can look up its embedding. IDs identify units; the numeric distance between IDs is not a semantic distance.

Run the lecture’s BPE example: what happens after merging t+h, th+e, and c+a for “the cat”?

Start with [t,h,e,c,a,t]. Merge t+h → [th,e,c,a,t]. Merge th+e → [the,c,a,t]. Merge c+a → [the,ca,t]. The lecture also lists an a+t merge across the corpus, but the “the cat” sequence stays [the,ca,t] in that selected order.

How does SentencePiece’s unigram method learn pieces differently from BPE?

BPE begins with small pieces and adds frequent adjacent pairs. The unigram method begins with many candidate pieces, learns probabilities for them, and prunes pieces that contribute least to modeling the training text. Character pieces provide a fallback for unfamiliar text. SentencePiece can implement either method and preserves the information needed to reconstruct the original text.

If one tokenizer uses 9 tokens and another uses 4, what percentage fewer tokens are used?

(9 − 4) / 9 × 100 = 55.6%\((9-4)/9\times100\approx55.6\%\) fewer tokens for that particular string. The new token count is 4/9 ≈ 44.4%\(4/9\approx44.4\%\) of the old count.

A vocabulary has 5,000 IDs and embedding dimension 128. Give the table shape, entry count, and output shape for 6 tokens.

Table shape: 5,000 × 128\(5{,}000\times128\). Entry count: 640,000. The 6-token input yields 6 vectors, or a 6 × 128\(6\times128\) array when tokens are rows.

How does a contextual embedding differ from a static embedding?

A static lookup assigns a token the same starting vector each time. A contextual representation is calculated after considering surrounding tokens, so “bank” can have different final vectors in “bank account” and “river bank.”

Compare encoder-only, decoder-only, and encoder–decoder models using one task each.

An encoder-only model reads an available input bidirectionally for a task such as sentiment classification. A decoder-only model uses prior tokens to generate a completion. An encoder–decoder model reads an input and generates a separate sequence, such as a translation.

What does the sequence probability equation say in plain language?

It says the probability of a complete sequence can be written as a product of conditional probabilities: first token, then second given the first, then third given the first two, and so on. Decoder-style generation follows this order when extending a prompt.
