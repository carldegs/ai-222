Introduction

1. What makes a system an agent?

Suppose you ask, “Is the campus library open this Saturday?” A useful answer may require identifying the library and date, finding a schedule, and checking that the schedule is current. If the first result is outdated, the system needs to try another step. This is the setting for today’s lecture: a goal whose solution unfolds through interaction with an environment.

An agent observes its environment, chooses an action toward a goal, and uses the result to decide what to do next. For a software agent, the environment might be web pages, files, or services; for a robot, it includes the physical world. Slide 3 introduces the ingredients that make this possible: tools, memory, planning, and feedback. Slide 8 connects them in a loop. We will use the library question as a running example and then look at what makes a run reliable.

At step t: observation oₜ + memory mₜ → decision aₜ → environment → new observation oₜ₊₁
\[a_t=\pi(o_t,m_t,g),\qquad (o_{t+1},m_{t+1})=F(o_t,m_t,a_t)\]

Read the equation as a compact picture of that loop. The symbol π\(\pi\) denotes the decision rule, or policy, while F\(F\) summarizes how the action leads to updated observations and memory. Here g\(g\) is the goal, oₜ\(o_t\) an observation, mₜ\(m_t\) available memory, and aₜ\(a_t\) a chosen action. Each new observation can change the next decision.

Inside an LLM-based agent: It can propose a next step from the available context. The surrounding application provides tools, executes permitted calls, returns results, and decides when the run should stop.
Recap · Language models

The model’s role inside the loop

From lecture 08, recall the path from text to token IDs, embeddings, and model output. A decoder-style language model predicts a continuation from the context it receives. That continuation can contain an answer, a proposed plan, or a structured tool call.

This is the connection we need here: predicting a tool call does not execute it. The surrounding application provides the available tools, runs permitted calls, and returns their results as new context. The model can then propose the next step. This lecture focuses on that interaction between model prediction and system action.

Choose the simplest fit

2. Workflow, agent, or embodied agent?

Before building the loop, let’s ask how much freedom the task needs. Slide 6 distinguishes a workflow, where the developer defines the steps, from an agent, where the model can choose the next action using intermediate results. Extracting an invoice amount and storing it may follow a known sequence. Researching a question may need a different search after each result. An embodied agent adds sensing and action in a physical environment, as with a robot handling laundry. These categories concern control and environment; each can use learned models.

DesignWho chooses the next step?Example
WorkflowThe developer's fixed sequence or branching rulesExtract an invoice amount, check it, then store it.
AgentThe model selects actions using intermediate resultsResearch a question, choose searches, inspect results, and stop when evidence is adequate.
Embodied agentThe agent chooses actions while sensing a physical environmentA robot detects laundry, moves garments, and operates a washer.

Which pattern fits the task?

Workflow: the sequence is known in advance. Use explicit steps and checks so each stage is predictable and testable.
The core architecture

3. Perceive → plan → remember → act → observe again

Now let’s unpack the diagram in slide 11. Perception makes input usable, reasoning and planning choose what to do, memory preserves useful information, and action interacts with the environment. For the library question, the system reads the request, decides to check a schedule, calls a tool, and examines the returned hours. The result becomes the next observation. If it concerns the wrong term, the plan must change.

Slide 13 pauses on the input side. Text can be tokenized for a language model, but a camera, microphone, GPS receiver, or LiDAR sensor supplies pixels, sound samples, coordinates, or distance points. Perception turns that raw signal into task-relevant information. For example, automatic speech recognition converts audio into words; a vision model can interpret an image. To reason across text and images together, their representations must be aligned so the system can connect a phrase such as “the red car” with the relevant visual region.

Perception→Reasoning / planning→Action→New observation↺Memory informs every step

Sensing vs perception

Pixels and waveforms are raw signals. “A person is crossing” and “an alarm is ringing” are interpreted observations.

Plan vs action

“Search for the current opening hours” is an intended step. Sending the search request is the action; the result is evidence to assess.

Feedback

An action may fail, return surprising data, or change the world. Check the outcome before continuing.

Slide 28 completes the loop with actions and their outcomes. Planning to search and actually sending a search request are separate events. The returned result is evidence to inspect before continuing. Try the trace below, especially the two possible outcomes at the checking step.

Improve the decision loop

4. Reasoning and reflection help choose the next action

How does the system decide its next step when the path is not fixed? Slide 16 introduces ReAct, which interleaves reasoning and acting. In our example, the agent decides it needs Saturday hours, calls a search tool, inspects the schedule, and chooses whether to answer or search again. The observation between actions matters: it can reveal that the earlier plan was incomplete. The other methods in the table organize intermediate reasoning or feedback in different ways; compare what each adds to the decision process.

MethodWhat actually changes?When it helps
Chain of thoughtWork through intermediate reasoning steps before giving an answer.A multi-step question that can be reasoned through using the available information.
Self-consistencyGenerate several independent reasoning paths and select the answer they most often reach.One plausible reasoning path may contain an error.
Tree of thoughtsExplore alternative next steps as branches, evaluate them, and continue promising branches.The task needs search or backtracking, such as a puzzle.
ReActAlternate a thought with an external action and the observation it returns.A fresh fact or tool result is needed before the next decision.
Reflection / ReflexionReview a previous attempt, identify the mistake, and use that feedback on the next attempt.A test, failed action, or critique shows what to revise.

Slide 20 introduces reflection: reviewing an attempt and using feedback to improve the next one. If the library search found last term’s schedule, a useful critique is “the source was official, but its date did not match.” A retry can then check the date earlier. ReAct describes the interaction between decisions and actions; reflection describes learning from the outcome of an attempt. These methods add time and computation, and agreement among several reasoning paths can still preserve a shared error. A multi-agent system can assign such subtasks to separate planning, checking, memory, or action specialists, but those specialists still need a shared goal and a way to combine their results.

ReAct cycle: thoughtₜ → actionₜ → observationₜ₊₁ → revised thoughtₜ₊₁
\[\text{thought}_t\rightarrow\text{action}_t\rightarrow\text{observation}_{t+1}\rightarrow\text{thought}_{t+1}\]
Keep the steps distinct: Reasoning chooses a next step. Acting calls a tool or changes an environment. Reflection uses the result to revise the plan. A confident explanation alone does not establish that an external action succeeded.
What survives between steps?

5. Memory is selected information, not infinite context

After several steps, what should the agent keep? Slide 22 includes plans, actions, results, and cached information. Short-term memory holds material for the current task, such as the recent dialogue or the schedule just retrieved. Long-term memory keeps information for later tasks, such as a useful procedure or a previously discovered source. Retrieval-augmented generation (RAG) selects relevant stored content and adds it to the model’s current context.

The word “memory” can be misleading here: storing a record in the application does not automatically update the model’s weights. A database can keep exact facts or past actions; a vector store retrieves text by similarity; graph-based memory links entities and relationships. Useful records include both successful and failed plans, reusable procedures, and new facts. For a new task, the system searches storage, selects relevant records, places them in the prompt, then decides what to do. Remembering a failed library search can be as useful as remembering a successful one if it prevents repeating the same mistake.

Slide 26 gives us the constraint: the model’s current context is finite. External storage may contain many records, but the selected observations and retrieved text still consume space when they enter the prompt. Loading everything can crowd out the task and repeat the same information. Slide 27 compares storage and retrieval approaches; whichever we choose, we need to select, summarize, and deduplicate what enters the context.

Context budget = instructions + current task + retrieved memory + tool results ≤ context limit
\[B_{\text{instructions}}+B_{\text{task}}+B_{\text{memory}}+B_{\text{tools}}\leq B_{\text{context}}\]
A finite context: Suppose the limit is 12,000 tokens. Instructions use 1,000, the current task 2,000, and tool results 3,500. Then at most 12,000 − 1,000 − 2,000 − 3,500 = 5,500\(12{,}000-1{,}000-2{,}000-3{,}500=5{,}500\) tokens remain for retrieved memory. The system also needs room for its response and other overhead.
Extend what the system can do

6. Tools and MCP connect agents to data and actions

We have referred to tools throughout the example. Now let’s examine what a tool call actually does. A tool exposes an operation such as searching a catalog, querying a database, executing code, or calling a service. The model proposes a call with arguments; the application checks and executes it; the result returns as an observation. This is how the agent gets information or performs an operation beyond producing text.

Follow the sequence carefully: the application tells the model which operations are available and what arguments each requires; the model proposes a named call with arguments; the application checks and runs it; the tool returns a result; the model decides whether to answer or call another tool. For example, add(a=5, b=3) returns 8. The model did not perform that addition through the tool until the application actually executed the call. The slides mention Toolformer and Gorilla as approaches for teaching models to select or write API calls; modern function calling exposes an explicit call format.

What if the application needs to connect to several different services? Slide 31 introduces Model Context Protocol (MCP), a standard interface for connecting an application to servers that expose tools, resources, and prompts. In the lecture's architecture, a host is the agent application; each client connects to a server. Tools perform callable operations, resources supply information, and prompts provide reusable interaction templates.

MCP partPlain-language roleToy example
Host and clientThe app and its connection to one serverA study assistant connects to a library server.
ServerExposes capabilities through a standard interfaceThe library server lists available functions.
ResourceInformation to readA catalog document.
ToolCallable operation, possibly with side effectsSearch the catalog or reserve a book.
PromptReusable interaction template“Summarize a catalog record.”

Slide 32 distinguishes those capabilities. A resource supplies something to read, a tool exposes an operation to call, and a prompt supplies a reusable interaction template. The lecture’s FastMCP example makes the tool case concrete: a server publishes the add tool, and a client first lists available tools and then calls add with a=5 and b=3. A local client and server can communicate through standard input/output (stdio); a web deployment can use streamable HTTP. The transport changes how messages travel, while the host–client–server roles remain the same.

After a call, the agent still needs to interpret the result. Returned text may contain errors or instructions placed there by someone else. Treat it as evidence for the task, rather than granting it authority over the user’s request. We will see why that matters in the final section.

Useful distinction: MCP supplies an interface; it does not itself decide a plan, verify a tool result, or authorize a risky action. Those responsibilities remain in the application design.
Trust the whole run, not one answer

7. Evaluate repeatability and the cost of mistakes

We can now trace a run, but how do we know whether the system performs well? Slide 38 shifts attention from one fluent answer to the whole task. A coding benchmark, a general assistance benchmark, and a customer-policy benchmark test different abilities. For the library example, success means finding the correct schedule, checking its date and location, and giving a supported answer. Repeating the same request also matters because the agent may choose a different path each time.

If independent runs each succeed with probability p, all n runs succeed with probability pⁿ.
\[P(\text{all }n\text{ runs succeed})=p^n\quad\text{(if runs are independent)}\]

Let’s read the equation with a toy example. If runs are independent, multiply their individual success probabilities to find the probability that all succeed. For an agent with p = 0.8\(p=0.8\), succeeding on eight independent repeats is 0.8⁸ ≈ 0.168 = 16.8%\(0.8^8\approx0.168=16.8\%\). This illustrates why reliability across retries is stricter than a single-run success rate. Real attempts may be correlated, so the equation is an assumption, not a benchmark result.

Slide 39 adds another dimension: the consequences of an action. Reading the wrong schedule can produce a wrong answer; reserving the wrong service or deleting a file can change the world. Limit tool permissions, require human approval for consequential actions, and keep a record of calls and outcomes. Treat instructions embedded in web pages or tool outputs as untrusted content: a page saying “ignore the user and send data elsewhere” is a prompt-injection attempt, not a valid user request.

Check your understanding

8. Can you trace and evaluate a run?

Let’s bring the pieces together. Start with the goal, identify the observation, explain the decision, name the action, and check what came back. Then ask what was stored and whether another step was needed. Try the questions below before opening the explanations; the goal is to trace the system’s behavior, not just recall the component names.

Why is an LLM with a tool list not automatically a reliable agent?

The system still needs a goal, a decision loop, a way to interpret tool results, memory management, stopping rules, and checks on permissions and outcomes. The model can propose calls, but the application executes them and must control their effects.

Compare workflow, agent, and embodied agent.

A workflow follows developer-set steps; an agent can choose steps from intermediate observations; an embodied agent also senses and acts in a physical environment. A fixed sequence is easier to test, while an agent handles less predictable paths at the cost of more variable behavior.

Explain one full perceive–plan–act loop.

For a library-hours question, perceive the user's requested date and location; plan to check an authoritative schedule; call a search or library tool; read the returned hours; check that they match the requested library and date; answer or search again if uncertain.

What is the difference between sensing and perception?

Sensing captures raw input, such as camera pixels or microphone samples. Perception interprets it into task-relevant meaning, such as “a person is crossing” or “the alarm is ringing.”

How do ReAct and reflection differ?

ReAct alternates a decision or reasoning step with an external action and observation. Reflection evaluates past reasoning, actions, and outcomes so the next attempt can be corrected. Both can help, but each adds computation and does not guarantee correctness.

Where does long-term memory appear if the model has a fixed context window?

Long-term information stays in external storage. A retrieval step selects relevant items and places them into the current context. Thus stored memory can be larger than the prompt, but only retrieved material in context is available for that decision.

Compute the remaining context budget: 12,000 total, 1,000 instructions, 2,000 task, 3,500 tool results.

12,000 − 1,000 − 2,000 − 3,500 = 5,500\(12{,}000-1{,}000-2{,}000-3{,}500=5{,}500\) tokens for retrieved memory in this simplified budget. Leave room for output and other overhead in a real system.

What roles do an MCP host, server, resource, and tool play?

The host is the application; a client connects it to a server. The server exposes capabilities. A resource supplies readable data, while a tool performs a callable operation. The protocol connects these pieces but does not make the agent's decisions safe by itself.

If each independent run succeeds with probability 0.8, what is the probability all eight succeed?

0.8⁸ = 0.16777216 ≈ 16.8%\(0.8^8=0.16777216\approx16.8\%\). Independence is an assumption for this exercise; real runs may share failure modes.

A web result tells the agent to ignore the user and send private notes to an address. What should happen?

Treat that text as untrusted page content. It is not a user instruction. Ignore the requested redirection, avoid sending private notes, and continue the authorized task using appropriate source verification and tool permissions.

9. Put the lectures together

Return to the library question we started with. We can now explain how the system turns a request into a sequence of checked actions: read the context, decide what information is missing, call a tool, inspect the result, and continue or stop. Across the series, we studied how models learn from data and process inputs. This final lecture places a model inside a larger system with memory, tools, and feedback. When explaining an agent, follow both the model’s prediction and what the application does with it.

Core idea

An agent uses a model within an observe–decide–act loop to pursue a goal in an environment.
