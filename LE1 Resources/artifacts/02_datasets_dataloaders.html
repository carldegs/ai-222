This lecture asks a necessary prior question: where do those trustworthy \(\mathbf{x},y\) pairs come from, and how do we feed them to the model?

Pipeline connection: Last lecture gave the learning objective. This lecture gives the data pipeline: collect or construct examples → label them → split them correctly → expose them through a Dataset → batch and prepare them through a DataLoader.

Dataset foundations

1. A dataset is samples plus labels

A dataset stores samples and their corresponding labels. The sample x could be an image, sound, text, sensor reading, or structured record. The label y is the answer the model is expected to learn: a class, a number, a bounding box, a sequence, and so on.

Essay move: “Data” is not only raw input. In supervised learning, its defining value is the input–target relationship \( (\mathbf{x},y) \). Explain what both x and y mean for the task.

2. Data quality: sufficiency, splits, and bias

A capable model cannot reach a target test performance if the dataset is insufficient, wrongly split, or systematically biased. These are not housekeeping details; they directly affect the validity of the test score.

Sufficiency

Enough relevant, varied, well-labeled data for a capable model to reach the required test performance. More data is not automatically better if it is repetitive, noisy, or irrelevant.

Train / validation / test

Train fits parameters. Validation guides design choices and tuning. Test is the final held-out evaluation. The exact ratio varies; leakage does not.

Bias

Sampling, exclusion, measurement, recall, association, and observer bias can make results systematically unrepresentative or unfair.

\(N=12{,}000\), split \(70\%/10\%/20\%\)
\(N_{train}=8{,}400,\quad N_{val}=1{,}200,\quad N_{test}=2{,}400\)
Non-negotiable: no duplicate samples across splits. A duplicate lets the model “see” test information during training and makes test performance look better than genuine generalization.

3. Public, custom, and synthetic datasets

Many projects begin with existing datasets. The lecture points to Hugging Face datasets, TorchVision, TorchAudio, TorchText, Common Crawl, and domain-specific collections. Custom data may need collection and annotation; synthetic data can create labeled examples efficiently, but must still resemble the real task distribution.

Likely comparison: Synthetic data gives scalable labels and controllable conditions. Real data gives natural variation. A strong answer explains that synthetic-to-real mismatch can damage generalization, so the choice depends on the target deployment distribution.

PyTorch data APIs

4. Dataset: the indexed collection

In PyTorch, torch.utils.data.Dataset is the map from an index to one example. It supports two core operations: __len__(), which reports how many examples exist, and __getitem__(index), which returns the sample and its corresponding label at that index.

len(dataset) -> number of examples
dataset[i] -> one (x_i, y_i) pair

Important distinction: a Dataset knows how to retrieve one example. It does not itself decide batching, shuffling, worker processes, or how a batch is assembled. That is the DataLoader’s job.

5. DataLoader: the efficient batch producer

A DataLoader wraps a Dataset and makes it iterable for training. It can form mini-batches, shuffle the sample order, use worker processes/threads, and collate individual examples into a batch—often including preprocessing.

6. Exam practice

Explain why a train/validation/test split is needed.

Training data fits model parameters. Validation data supports choices such as architecture or hyperparameters without touching the final test set. Test data is held out for the most honest estimate of generalization. State that samples must not be duplicated across splits, because this causes leakage.

Compare Dataset and DataLoader in PyTorch.

A Dataset stores or knows how to retrieve individual examples, typically through __len__ and __getitem__. A DataLoader wraps it into an iterable that handles mini-batching, shuffling, worker-based loading, and collating. Dataset answers “what is example i?”; DataLoader answers “what batch comes next?”

Why can a large dataset still fail to generalize?

Quantity alone does not guarantee sufficiency. The data may be biased, mislabelled, unrepresentative of deployment, duplicated across splits, or lack relevant coverage. Relate the answer to the IID/generalization concern from the previous lecture.

A dataset has 50,000 samples. Give the counts for an 80/10/10 split.

40,000 training; 5,000 validation; 5,000 test. In a real answer, add that a ratio is a design choice, not a universal rule, and that duplication across splits must be avoided.

Now that data can be retrieved as batches of tensors, the next question is: what model transforms each batch of inputs into predictions? The MLP lecture introduces the simplest deep neural network built from linear layers and nonlinear activations. Keep this link in mind: a DataLoader supplies a batch of x values and labels y; an MLP computes y-hat; the loss then compares y-hat with y and updates theta.

\(\rightarrow\) MLP computes \(\hat{\mathbf{y}}=f(\mathbf{x}_{batch},\boldsymbol{\theta})\)
\(\rightarrow\) loss \(\ell(\mathbf{y}_{batch},\hat{\mathbf{y}})\)
\(\rightarrow\) optimizer updates \(\boldsymbol{\theta}\)
